# 08 · 实现原则（给人和 AI 的同一份红线）

> 本文不是写法教程（那在 `docs/02`），是**过程纪律**。
> 每一条都对应本项目真实发生过的返工；写在这里的唯一目的是别再犯。
> AI 读这份文件时，请把它当**验收标准**，而不是背景资料。

---

## 0. 一句话

**复刻的是语义，不是形状。**

形状可以不同（Rust 没有 TS 的类型系统，`Rc<dyn Fn>` 也没有 TS 的结构类型），
但语义必须逐条对得上——对不上的地方要能说出"为什么这里允许不同"。

判断"我对上了"的标准不是"看起来像"，而是：**能指回 TS 的哪一行，且行为可观测地一致。**

---

## 1. 结构：声明式树，不写过程式装配

**正例**

```rust
rect_node! {
    ..rest,
    width: 342,
    children: vec![label("标题"), text_field(arg)],
}
```

```rust
#[rec]
fn editor_panel(rest: Node2Props) -> Fc { .. }
```

**反例**（真实发生过：连续三轮把组件写成 builder / controller / pipeline）

```rust
// 不要：构造 → 设属性 → 挂子节点
let mut n = Node::new();
n.set_width(342.0);
n.append(label("标题"));
mount(n);              // ← 一旦出现 .mount()，就已经在写命令式框架了
```

**自查**：一个组件函数体里如果出现"创建对象 → 改字段 → 追加子节点"三段式，
或者出现 `set_*` / `append` / `mount` / `pipeline` 这类词，就是退化了。

**字段写表达式，不写值**（`#[getter]` 字段由宏包 `move ||`）：

```rust
width: vp_w.get().0,        // ✅ 每次布局时现读 → 窗口 resize 会跟随

let w = vp_w.get().0;       // ❌ 提前求值，响应性在这一行就断了
.. width: w,
```

### 1.1 测试与文档示例同样是范例

一处 `Node2Props::builder()` 出现在 `#[test]` 或 rustdoc 里，下一个人（或 AI）
就会照着抄——**示范价值不分生产/测试**。

`Props::builder()` / `Props::build()` 已标 `#[doc(hidden)]`：它们是 `xxx! { .. }`
宏展开的机械通道（`node2!` 展开出来就是 `Node2Props::builder()..build().build()`），
不是给人和 AI 手写的入口。手写即违规。

测试里若确实需要**一份 props**（例如喂给 `..rest`：宏产节点、不产 props），
写结构体字面量，并注明它是数据而非装配：

```rust
// ✅ 一次性数据表达式
let base = RichTextNodeArg {
    spans: Some(Rc::new(|| vec![RichTextSpan::text("来自 rest", Color::BLACK)])),
    ..Default::default()
};

// ❌ 过程式装配
let base = RichTextNodeArg::builder().spans(|| vec![..]).build();
```

自检命令：`grep -rn "::builder()" crates/` —— 命中只应出现在注释里。

## 2. 尺寸：先问"这是输入还是结果"

| 类别 | 处理 | 例子 |
|---|---|---|
| **结果** | 交给布局，一个像素都不写 | 父分配的宽度、子节点撑起的高度、flex 交叉轴 |
| **输入** | 必须写，并注释为什么 | 空态下量不出尺寸的编辑器、图标、最小点按区 |

**真实教训**：`tall_items` 的行节点写了 `layout: flex!{}`，宽度塌回文本宽 78px。
TS 里那些矩形**不写 layout**（绝对定位 → `sizeFromParent` 拿父分配的 336px）。

**口诀**

- 有 `layout` = **容器**（`allows_size_from_children()` 为真 → `sizeFromChildren`）
- 无 `layout` = **被摆放的子项**（`sizeFromParent`，跟随父分配）

**宽度要跟着父走的行，不要挂空 `flex!{}`。**

**另一面**：也不能反过来教条。`EditableTextController::size` 在无显式宽高时按段落
量出来的宽高报数，空文本 = 0 宽——这时 `width: 356-14` 是**必需输入**，不是手算偷懒。
写之前问一句"这个值如果是 0，会怎样"，答案决定它该不该写。

## 3. 对齐是双向的，不是单向抄

三套实现互检：Rust `wy-mve` / TS `canvasRender2` / Kotlin `wy-helper-kotlin`。
**谁错改谁**，包括 TS 和 Kotlin。

**真实案例**

- TS `todo-editor.ts` 备注框占位文案承诺"Ctrl+Enter 加入列表"，却没传 `onSubmit`
  → 按了没反应。**改的是 TS**，Rust 侧同步补。
- TS 里 `ScrollContent.drawAtParent` 承担裁剪，Rust 早先压在容器 `clip` 上
  → 嵌套滚动内容溢出。**改的是 Rust**。

**禁用的挡箭牌**

- "TS 就是这么写的"（TS 也会有 bug）
- "Kotlin 也这样"（同上）
- "Rust 里这样更自然"（那就得说清语义差别在哪）

发现单侧缺能力时，先判断是**故意设计**还是**漏了**，再动手。

## 4. 一一对应，不发明抽象

- 类型继承：`#[rec(extends = base, omit(k))]` ↔ TS `extends Omit<Base, 'k'>`
- 参数名、层级、默认值都要能对上；对不上要写在审计文档里

**真实教训**：早先自创了 `scroll()` + `ScrollOpts`（TS 里根本不存在），
把方向反转、滚动条坐标手算全塞进去，结果三处行为都对不上。

**规则**：引入任何"更地道的 Rust 写法"前，先能指回 TS 的哪一行。
指不回去，就去 `docs/05` 记一笔"这里我们不同，原因是 X"，不要偷偷改。

## 5. 裁剪 / 绘制顺序：照抄 `save/restore` 的位置

TS `assemble.ts` 的顺序是**语义**，不是风格：

```
save → drawAtParent（剪） → translate → draw → restore
```

- 裁剪属于**子节点对自己子树**的约束，用的是**父**内盒；
- 它发生在 `translate` **之前**——放错位置就会拿子节点坐标去剪父框。

对应 Rust：`Node2Props::clip_to_parent`，在父的绘制循环里于 `push_transform` 之前压栈。
容器的 `clip` 是另一件事（剪自己），不要混。

## 6. 事件语义：一次物理动作 = 一条语义事件

**真实教训**：winit 对同一枚键发 `Pressed` + `Released` 两条 `KeyboardInput`，
两条都转发 → 编辑器里方向键"按一下走两格"、退格删两个字符、回车提交两次。

规则：

- `handle_key_event` 只在**按下**时调一次；松开不产生按键语义。
- 新增任何派发入口前，先数一数同一个物理动作会被调用几次。
- 字符输入走 IME `Commit`，不要在键盘路径里再插一次（`ime_guard` 就是为此存在）。

## 7. 缓存与优化：必须回答"什么让它失效"

**真实教训**：绘制缓存 `RecordMemo<Scene>` 的失效条件只有**信号**，
而视口尺寸不是信号 → resize 后复用旧 Scene：
"窗口拉大，内容不动；点一下（碰巧改了某个信号）才跟上"。

规则：

- 引入缓存前，列出**全部输入维度**：信号 / 帧环境（w、h、scale）/ 字体度量 /
  locale / 主题。信号之外的那些，必须有显式 `invalidate` 的口子，并在变化处调用。
- 优化不许改变可观测行为：加缓存前后跑同一张快照，图元数与 diff 必须一致。
- 缓存失效是**一次性**的：置脏 → 重录 → 清脏，别写成永久重录（也别说"反正没错"）。

## 8. 不猜：用可观测证据定位

- 出快照 + 像素/band 分析 + 几何打印（用**临时**开关，收尾必删）
- 一个现象追到**根因**，别停在"改一下看着好了"
- 分层实验：换 spacer / 去 direction / 去 layout，一次只动一个变量

**真实案例**：嵌套滚动里"内层条目宽度塌到 78px"，先是以为裁剪问题，
补 `clip_to_parent` 后仍在；逐层实验才定位到行节点的空 `flex!{}`。
**两个根因叠在一起时，第一个修好会让人误以为没修对。**

报告成果要带证据：图元数、`diff = 0`、测试名、手算对照。

### 8.1 先怀疑"没有字形的输入"

文本类缺陷有个固定套路：**空行、空文本、纯空白**会让所有基于字形/坐标的
反查失效（没有簇可命中，于是落到"最近"或"文末"兜底）。

- 行号必须按**偏移**算（`line_index_of_byte`），不能拿光标矩形去碰行盒；
- 行内取点必须把**行范围当硬边界**（`position_in_line`），空行返回行首；
- 判定"有没有内容"用 `is_blank_line`，不要用 `rects_for_range(..).is_empty()`
  反推——"没有矩形"既可能是空行，也可能是越界。

- 测试锁**外部可观测性质**：裁剪盒坐标、焦点序、宽度没塌、提交次数、缓存重录次数。

修 bug 没有伴随测试，视为没修完。

## 10. 单一可置信信号源（派生量只读原子真相源）

**一句话**：每个**连贯状态组**只准有一个**原子信号**当唯一真相源；所有派生量都是
读它的**纯派生**（getter / memo），绝不自己再存一份中间信号，也绝不绕过真相源
去挖一个藏在 `RefCell` 里的内部对象现算。

**正例（编辑器光标 / 选区，三套实现都如此）**

```rust
// 唯一真相源：一个原子信号，整对写入
caret_pair: Signal<Option<(usize, usize)>>,
// 派生量：纯 getter 读真相源，不在响应式图外散落计算
fn anchor_index(&self) -> Option<usize> { self.caret_pair.get().map(|(a, _)| a) }
fn cursor(&self) -> usize { self.anchor_index().unwrap_or(0).min(self.text_len()) }
```

Kotlin `caretPair: Signal<Pair<Int,Int>?>`、TS `caretPair = createSignal<[number,number]|null>(null)`
都只有这一个原子源；`anchorIndex` / `focusIndex` / `cursor` / `localSelStart` /
`cursorSelPair` 全是读它的纯 getter / 箭头函数。**没有** `anchor_signal` + `focus_signal`
两路，**没有** `cursor` 单独成信号被各处写。

**反例（本项目真实发生过的闪退根因）**

```rust
// ❌ 把含信号的整块逻辑塞进 RefCell 内层对象
struct EditCore { anchor: Signal<...>, focus: Signal<...>, ... }
core: RefCell<EditCore>,
// 派生量经 core.borrow() 散落读取，游离在响应式图之外；
// 且 Signal::set 会同步 flush 观察者，观察者回头借 core → RefCell already borrowed → 闪退
```

**三条硬规矩**

1. **一个状态组 = 一个原子信号**。光标 + 选区这种天然一对的量，存成
   `Signal<(anchor, focus)>`（或 `Option<(a, f)>`），**整对原子写入**，
   永远不出现"anchor 新了 focus 还是旧的"半更新中间态。
2. **派生量不落信号、不落字段**。需要 `anchorIndex` / `cursor` / `localSelStart` 时，
   现读真相源现算（纯 getter / memo）。它们不是独立事实，不该拥有自己的信号或可
   变字段。组合态 `composingText` / `composingCursorPos` 是**另一组**独立事实，
   各自单信号即可（对齐 Kotlin / TS），不要和光标真相源混为一谈。
3. **信号是节点 / 控制器的直接字段，不包进 `RefCell` 内层对象**。
   真相源一旦躲在 `RefCell` 里，`set` 触发的同步 flush 会让观察者回头借同一个
   `RefCell` 而 panic。变更后若必须借内部可变数据，先**释放借用**再 `publish`
   到直接字段信号（见 `EditableTextController::publish_sel`）。
4. **流是单向的：纯逻辑层（如 `EditCore`）→ `publish` → 真相源信号，绝不回灌**。
   曾经在 `sync_params` 里把控制器信号 `caret_pair` 又写回 `EditCore`（`set_pair` /
   `clear_pair`），这是双向同步——在 `edit` 的 `write_text` 经外部 `text` 信号触发
   **同步 flush** 时，`caret_pair` 还是旧值，回灌把刚算好的新光标覆盖回旧值，
   于是换行后光标停在上一行、上下键因光标落在空矩形退化成乱跳。修复后：删掉回灌，
   且 `edit` 必须先 `publish_sel` 再 `write_text`，保证任何 flush 期间真相源已是新值。
5. **真相源信号要在"读它的那一层"被直接 `get()`，才能成为该层的重绘依赖**。
   绘制走 `RecordMemo`：只在**被读到的信号**变化时重录。若某层只经一条中间 memo
   间接用到真相源，而该 memo 在"塌缩态"下输出不变，那一层就收不到变化、复用旧帧。
   编辑器曾因此：光标移动（塌缩光标）只改 `caret_pair`，但 `draw` 经 `range_of` 读的是
   **选区 memo**，塌缩光标下它不变 → 绘制 RecordMemo 不重录 → 上下键光标消失。
   修复：在 `draw` 里**无条件 `self.cursor()` 一次**，让 `caret_pair` 直接成为绘制依赖；
   另在 `move_to` / `extend_to` 后 `restart_blink`，移动后光标即时可见。

6. **派生几何也要单一源：同一段光标 / 选区矩形算法，只能有一份实现，禁止在 `draw`
   里再抄一份 `rects_for_range` 内联副本**。
   编辑器曾因此：光标矩形算法在 `caret_rect()` 里有一份（含末尾空行 / 行首兜底），
   而 `draw` 的光标绘制段又**另写了一份** `rects_for_range` 内联、**漏掉了换行分支**——
   于是逻辑光标虽已前进到新行（offset 正确），视觉矩形却被画在上一行末尾，表现为
   "换行后光标没到下一行"。修复：删掉 `draw` 内联副本，直接复用 `caret_rect()`。
   判据：任何 `rects_for_range` / `getRectsForRange` 的调用若出现在两处且语义略有出入，
   就是分裂实现，必须合到一处。

**架构偏离提醒（与 TS / Kotlin 的差距）**：TS `editor.ts` 与 Kotlin `EditableTextNode.kt`
都把 `caretPair` 作为**直接被编辑动作 `set` 的原子信号**（`caretPair.set([a, f])`），
派生量全是纯读。Rust 这边目前多了一层 `EditCore` 结构体（anchor / focus / composing /
preferredX 为普通字段）+ `publish_sel` 把核内态**拷**到控制器信号——这是"回到 Rust 结构体
编程"的额外发明，不是 TS / Kotlin 的做法，也增加了"核 ↔ 信号"两步不一致的风险。功能上
它能跑（当前 bug 不在它），但属于 **over-engineering**，后续应把 `caretPair` 收为编辑动作
直接 `set` 的信号、去掉 `EditCore` 这层中间态（即用户说的"不必回到 rust 结构体编程"）。

**豁免项（别过度 faithful）**：Kotlin / TS / Rust 三处都把 `compositionBase`
（IME 替换原文，供取消还原）与 `preferredX`（上下移视觉列提示）写成**普通可变字段**
而非信号。它们是真正独立的小事实、不是任何真相源的派生副本，所以不违背本原则——
不要把它们也信号化。

**自查**

- `grep -rn "RefCell<.*Signal\|Signal<.*>.*RefCell" crates/`：生产代码只应命中
  `text_defaults.rs` 那种"全局单例懒初始化"（`thread_local! { static X: RefCell<Signal<_>> }`），
  **不应**命中"含信号的业务结构体被塞进 RefCell"。
- 一个状态组若同时存在两个都能被写、彼此又该保持一致的信号，就是分裂真相源，必须合成一个。
- 派生 getter 里若出现 `mut` / 缓存字段 / `.set(`，说明它偷偷变成了第二真相源，违例。

**规则**：引入任何"更地道的 Rust 写法"前，先能指回 TS / Kotlin 的哪一行——
它们的 `caretPair` 就是唯一真相源，派生全是纯读。指不回去，去 `docs/05` 记一笔。

## 11. 收尾三件套 + 一致

1. `cargo fmt --all`
2. `cargo clippy --workspace --all-targets`（不能有新告警）
3. `cargo test --workspace --lib` + 相关示例测试 + 快照 diff
4. 删掉临时调试开关（`--dump` 之类）
5. 注释、文档、截图**三者不许超前于实现**——这是 `docs/06 §4` 记录过的问题
6. 跨仓库改动（TS 同步修）要确认真的落盘（`git status` / `tsc --noEmit`）
7. `grep -rn "::builder()" crates/` 只命中注释；测试里也没有装配式写法

## 附 A · AI 特有的失效模式（每次提交前逐条自查）

| # | 失效模式 | 症状 | 对策 |
|---|---|---|---|
| 1 | 把声明式退化成 builder/pipeline | 出现 `set_*`/`append`/`mount`/controller | 回到 §1，函数体只留一棵树 |
| 2 | 用"机制映射"替换语义 | 注释写得很像对上了，行为不同 | 回到 §4，指回 TS 行号 |
| 3 | 只看单侧源码 | 对着 Rust 改 Rust，越改越偏 | 回到 §3，三方互检 |
| 4 | 加优化不列失效条件 | resize/字体/主题不刷新 | 回到 §7，先列维度表 |
| 5 | 声称通过但没跑 | "应该没问题" | 回到 §11，贴命令与结果 |
| 6 | 交付留调试代码 | `--dump`、临时 `eprintln` | 收尾清单 |
| 7 | 把"看起来一样"当"行为一样" | 跳过快照 diff | 出图，比图元数 |
| 8 | 遇到歧义闷头猜 | 大改方向错了 | 先问，再写 |

**最容易复发的是第 1 条**：只要开始写"构造 → 配置 → 挂载"，就已经跑偏了，
停下来重写成 `node2! { }` / `#[rec] fn`。

## 附 B · 动手前五问

1. 这个组件在 TS 里长什么样？逐行读过没有？
2. 我写的每个尺寸，是**输入**还是**结果**？
3. 我引入的抽象，TS 里有对应物吗？没有的话，凭据是什么？
4. 我加的缓存，什么情况下会失效？失效口子在哪被调用？
5. 改完我用什么证据证明它对了？（测试名 / 图元数 / diff / 手算）

五问有一个答不上来，就先别写代码。
